이번 카드값이 얼마 나올지,
마감일 전에 알 수 있게.

신용카드의 statement closing date 기준으로 지출 사이클을 추적하고, 영수증 사진을 AI로 파싱해 품목별로 자동 기록하는 iOS·Android 모바일 앱. 아래 데모를 직접 눌러보면서 읽어보세요.

플랫폼 Flutter · iOS + Android 스택 Flutter · FastAPI · Supabase 통화 USD

배경 & 시장 조사

기존 가계부 앱의 한계

  • 집계 기준의 한계: 시중 가계부는 예외 없이 달력 월 기준으로 집계하지만, 카드 사용자의 실제 관심사인 "이번 카드값"은 statement closing date 기준으로 확정됨 (예: closing 21일 → 실제 청구 단위는 전월 22일~당월 21일). 이 불일치로 사용자는 도구를 쓰면서도 가장 중요한 질문에 수동 계산으로 답해야 함.
  • 입력 방식의 한계: 거래 단위 기록만 지원해 품목 데이터를 남기려면 메모란 수동 타이핑 — 현실적으로 "장보기 $52"로 뭉뚱그려지고 분석 정밀도는 상점 단위에서 멈춤.
  • 이 두 한계가 각각 핵심 기능(closing date 사이클 / 영수증 AI 파싱)으로 이어짐. 개발자 본인이 실사용 중 확인한 문제로, 첫 사용자로서 검증 루프 최단.

시장 현황 (2026.08) — 개별 기능의 경쟁자는 있으나 조합은 비어 있다

  • 수요 신호: 커뮤니티에서 카드별 billing cycle 탭을 나눈 직접 제작한 엑셀이 공유됨 — 제품 공백의 전형적 신호. "카드들 사이클이 제각각이라 월말 숫자가 머릿속과 안 맞는" statement-cycle confusion이 명명된 문제로 존재.
  • 포지셔닝: 홍보 리드는 파싱이 아니라 사이클 — "카드값이 얼마 나올지 마감 전에 아는 앱". 파싱은 "입력이 편한 이유"로 뒤에.
  • 경쟁 앱 리뷰에서 배운 설계 요구사항: 할인/음수 라인 처리 실패 → 합계 불일치 불만 (프롬프트에 명시 + total 검증 배지) · 축약 표기("WHL MLK 2%") 그대로 저장되는 불만 (품목명 정규화 명시) · 공격적 페이월 반감 (본 제품은 넉넉한 무료 티어 + 수동 입력 상시 가능) · 데이터 판매 불신 (프라이버시 정책이 셀링 포인트) · 상위 앱도 실측 92~94% (확인 화면 = 필수 안전망).
  • 리스크: 공백의 이유가 "아무도 안 해서"인지 "수요가 작아서"인지 미검증 — 학기 프로젝트 + 캠퍼스 소프트런칭 규모가 검증에 적합.

제품 개요

타겟 — 신용카드를 주로 쓰면서 "이번 카드값이 얼마나 나올지"를 실시간으로 알고 싶은 사람. 본인 + 미국 거주 초기 테스터가 첫 사용자.

핵심 차별점

  • 카드별 closing date 기준 사이클 측정 — 기존 앱은 대부분 매월 1일 고정. 결제금액이 확정되는 날 기준으로 "예상 카드값"을 마감 전에 보여준다.
  • 신용카드 vs 현금성 지출(debit·cash·Zelle) 구분 — 결제수단별 색상이 앱 전체를 관통하는 색 언어.
  • 영수증 업로드 → AI 파싱 → 품목별 자동 카테고리 분류.
  • Post-MVP 공유 가계부 — 커플/룸메이트용 + 가상 모임통장 (기록·잔액 추적만, 돈 보관은 안 함).

플랫폼 전략 확정

  • Flutter 단일 코드베이스로 iOS·Android 동시 지원.
  • 카메라 촬영·갤러리 선택·딥링크 등 모바일 네이티브 기능을 직접 활용.
  • 초기 MVP는 웹 없이 모바일 앱에 집중하고, TestFlight·Google Play 테스트 트랙을 거쳐 스토어 출시.

범위 & 과금 구조

  • 결제수단 등록: 신용카드(closing date 지정) / 현금성 — 카드별 색상 지정
  • 지출 수동 입력: 금액·카테고리·결제수단·날짜·메모 (3탭 이내)
  • 카드별 사이클 뷰: 누적액 · D-day · 진행률
  • 통합 대시보드: 30일 지출, 카드 vs 현금, 카테고리 분포, 일별 바 차트
  • 카테고리 CRUD — 기본 12개 자동 생성
  • 영수증 업로드 → Vision LLM 파싱 → 품목/가격/카테고리 JSON
  • 확인 화면: 품목별 수정 후 일괄 저장 + total 검증 배지
  • 개인화: 수정 내역을 merchant+품목 규칙으로 축적
  • 무료 파싱 카운팅 (유료화 시 그대로 재사용)
  • Pro 유료 플랜 — App Store / Google Play 인앱 구독, 회원만 결제 (구매 귀속·복구·환불) 수치·결제 레이어 미확정
  • 파싱 크레딧 팩(+20장 등) — "50장 소진 유저 비율" 확인 후
  • 공유 가계부 (커플/룸메이트용 + 가상 모임통장) + 정산 뷰 — 홈에 ledger switcher 추가. API는 처음부터 /ledgers/{id}/... 경로로 설계 (MVP 코딩 시점부터). Pro 100장 상향 or "멤버 수 × 50장" 검토
  • Pro 기능 — 캘린더 연동: 카드 마감일·예상 카드값·반복 결제일을 Apple/Google 캘린더와 연동하는 기능 검토. 네이티브 푸시 알림과 역할을 구분해 필요성 검증 후 구현.
  • 환불/취소·반복 지출 · 네이티브 확장 기능(푸시 "마감 D-3", 홈 위젯, 딥링크) 검토
  • 은행 연동(Plaid 등) — 비용·심사 이슈. 카드번호를 받지 않음 = 민감정보 제로.
  • 예산 알림, 다국어. 통화는 USD 단일(currency 컬럼만 확장 대비 유지).

인증 아키텍처 결정
Email / Password + Email Verification 확정
회원은 이메일과 비밀번호를 사용하고 이메일 인증을 완료한 뒤 계정을 활성화. 비밀번호 해싱·credential·session은 Supabase Auth가 관리하며 public.users에는 비밀번호 관련 컬럼을 두지 않음.
Guest 모드 확정
Guest 데이터는 Flutter 기기 SQLite에 저장. 회원 전환 시 인증된 user_id의 서버 데이터로 마이그레이션.
User ≠ Email 확정
앱 데이터 소유자는 Supabase Auth UUID. public.users.id = auth.users.id로 연결하고 이메일을 FK로 사용하지 않음.
Social Login / Account Linking 확장 가능
Google·Apple Sign-In은 Supabase provider로 추가 가능. 서로 다른 provider 계정 자동 병합은 하지 않고 linking 기능은 별도 요구사항으로 다룸.
인증 이메일 발송 방향 확정
Production에서는 Resend 같은 Transactional Email Provider를 Supabase custom SMTP에 연결. 인증 메일 요청에 rate limit과 resend cooldown 적용.
Supabase 의존성 경계
Database 확정
Supabase Managed PostgreSQL을 사용하지만 앱 데이터는 Flutter → FastAPI → Service → Repository → SQLAlchemy → PostgreSQL 경로로만 접근.
Auth 확정
Flutter는 Supabase Auth SDK로 로그인하고 JWT를 FastAPI에 전달. FastAPI 공통 Auth dependency에서 검증.
App Profile 확정
auth.users는 credential/identity를 관리하고 public.users는 nickname·plan 등 앱 전용 프로필을 관리. 동일 UUID로 1:1 연결.
Storage 확정
Supabase Storage 호출은 FastAPI의 Storage Service / Wrapper에 격리하여 추후 S3·R2로 교체 가능하게 유지.
Gemini 확정
Gemini SDK·API key·timeout·retry는 공통 integration에서 관리. Prompt·category logic·total validation은 Receipt Service가 관리.
시스템 아키텍처 결정
데이터 단일 경로 확정
읽기·쓰기 모두 FastAPI 경유. Flutter 앱이 Supabase와 직접 통신하는 건 Auth뿐.
로직(사이클·quota·멤버십)은 FastAPI에 모으고, RLS는 우회 접근을 막는 추가 방어 계층으로 유지.
이미지 업로드는 서버 경유 확정
프론트 → FastAPI → Storage. 모든 이미지가 검역(재인코딩·EXIF 제거·리사이즈)을 반드시 통과.
presigned 직접 업로드는 검역 우회 경로라 기각.
파싱은 "확장 가능한 동기" 확정
MVP는 동기(타임아웃 30초, FastAPI async라 LLM 대기가 서버를 막지 않음). API 계약만 비동기 호환 — POST /receipts → {receipt_id, status}, GET 폴링 지원.
큐 도입 시 프론트 무수정, 백엔드는 인라인 호출→큐 등록만 교체. 오늘 비용 ~0으로 문만 내고 큐는 짓지 않음. 연결 끊김은 상태 머신(draft 서버 보존)이 방어.
스케줄 작업 (7일 청소) 미확정 · 유력안
GitHub Actions 스케줄이 보호된 /internal/cleanup을 하루 1회 호출 — 무료, 실행 로그가 GitHub에 남음, 서버 수명 무관.
탈락안: pg_cron 단독(Storage 이미지 못 지움) · lazy cleanup(프라이버시 약속 위반 소지) · APScheduler(무료 티어 재시작 환경 불안정). 정리 로직은 순수 함수라 스케줄러 교체 시 재사용.

PK 기본키 FK 외래키 선 = 1 : N 관계 · receipts → transactions는 영수증 한 장이 여러 지출 row를 낳고, income_sources → income_records는 반복 수입 규칙과 실제 수입 기록의 관계

설계 원칙

  • 사이클은 저장하지 않는다 확정 — closing_day 하나로 조회 시점에 계산(Demo A = 이 명세). 마감일 변경 시 과거 재계산 불필요. UI 용어는 "결제일"이 아닌 "명세서 마감일".
  • 지출과 수입을 분리 — transactions는 지출 전용. 반복 수입 규칙은 income_sources, 실제 수입은 income_records에 저장. 비정기 수입은 source 없이 record만 생성 가능.
  • Receipt는 원본 보관함 — 영수증 1장 → 품목별 N개 transaction. Tax·Tip도 별도 row로 저장해 합계 검증 가능.
  • 인증 정보는 Auth에 격리 — 비밀번호·identity·session은 Supabase Auth가 관리하고 public.users에는 앱 프로필만 저장.
  • 카운터 컬럼을 두지 않는다 — 파싱 사용량은 receipts COUNT, 카드 수는 payment_method COUNT로 파생. 카운터는 동기화 버그의 원천. 게이팅 수치는 미확정
💰 Income 규칙
정기 수입은 frequency + reference_date를 필수로 받고, next_expected_date는 FastAPI가 계산한다. 실제 입금은 income_records에 저장하며 예상 금액과 실제 금액을 분리한다. Tip·cashback 같은 비정기 수입은 income_source_id = null로 직접 기록할 수 있다.
알림 시간은 사용자별 설정으로 저장하지 않고 앱 정책으로 고정한다. Flutter가 next_expected_date를 받아 정해진 시간에 local notification을 예약하며 MVP에서는 별도 notification table을 만들지 않는다.

🗓 홈📊 대시보드＋💳 내 지갑⚙️ 설정
UI 용어 — 화면엔 "결제수단" 대신 "내 지갑", 등록은 "카드 추가" (실결제 연동으로 오인 방지). DB/코드는 payment_method 유지 — UI 용어와 코드 용어 분리. 문서 내 "결제수단"은 개념 지칭.
S1홈 — 통합 월간 캘린더▶
  • 날짜 셀엔 결제수단별 색 도트만 (금액 없음). cash-like도 색 보유. Demo B가 이 명세.
  • 마감일 셀 = 카드 색 배경 + 사이클 누적액만 — 카드명 생략, 색이 식별. 하단 색 범례.
  • 오늘은 테두리 강조. 하단 패널: 선택 날짜 거래 리스트(도트 포함). 상단에 그 달 합계.
S2대시보드▶
  • 스크롤: 사이클 카드 → 일별 바 차트 → 카테고리 도넛 → 현금성 박스.
  • 사이클 카드: 색 점 + 이름 + D-day + 누적액(큰 숫자) + 진행률 바 + 기간.
  • 일별 바 차트(30일): 결제수단 색 스택 — 주간 패턴·과소비 구간 시각화.
  • Phase 2~3 사이클 페이스 비교: 지난 사이클 같은 시점 vs 현재 — 카드값 초과를 마감 전 예고.
S3입력 플로우▶
  • ➕ 탭 → 시트: "직접 입력 / 영수증 촬영". 영수증 옵션에 남은 파싱 수 상시 노출("7장 남음").
  • 직접 입력: 금액 크게 → 결제수단 칩 → 카테고리 칩 → 날짜/메모. 3탭 이내. 칩 색 = 카드 색.
S4영수증 파싱 확인▶
  • merchant/날짜/결제수단 헤더 + "AI 분류" 배지. 품목별 이름/가격/카테고리 칩(탭 변경).
  • Tax·Tip은 회색 라인 구분. 하단: 합계 + total 일치/불일치 검증 배지.
  • "품목 추가" 보조 + "N건 모두 저장" 주 버튼. 원본은 "이미지 보기".
S5내 지갑 — 카드 추가▶
  • 타입 2택이 맨 위 — 현금성 선택 시 마감일 섹션 숨김(조건부 폼).
  • 마감일 1~31 그리드 + "결제일(due date)이 아니에요" 경고.
  • 선택 즉시 "현재 사이클: 8/6 – 9/5" 실시간 미리보기 (Demo A가 이 UX).
  • 색상 6택 — 캘린더·대시보드와 연동.
S6한도 게이트 2종 수치 미확정▶
  • 파싱 초과: "무료 파싱을 모두 사용했어요 (10/10)" — 주 버튼 = "직접 입력하기" (막힌 사용자 먼저 구제), 보조 = "Pro 보기 · 월 50장". 이어서 영수증 이미지(핀치 줌) 보며 직접 입력. 이미지는 저장 → "유료 전환 시 과거 영수증도 파싱" 업셀.
  • 카드 초과: "무료 플랜은 카드 2개까지" — 파싱 팝업과 동일 패턴 재사용.
S7온보딩 (2단계)▶
  • 시작: 가치 제안 + [계속하기: Email OTP / Google / Apple] / [가입 없이 둘러보기] — 기기 저장이며 앱 삭제·기기 변경 시 소실 가능함을 명시.
  • 첫 카드 등록: "카드번호는 필요 없어요 — 이름과 마감일만". 빠른 선택(1/5/15일/직접), 건너뛰기 허용.
  • 비회원 → 회원 전환 시 기기 SQLite → 서버 마이그레이션 (전환율 핵심 장치).

영수증 파싱 플로우 Phase 2

Interactive Flow
단계를 눌러보세요 — 샘플 영수증이 파이프라인을 통과합니다
  • 카테고리 소유권 3층: 앱이 기본 세트 → 사용자 CRUD가 최종 → AI는 목록 안에서 추천만(임의 생성 불가) → 수정은 규칙으로 축적.
  • 비회원 파싱: 이미지는 서버 메모리에서만 처리, 파싱 즉시 삭제 — 디스크에 쓰지 않는 구조.
  • 실패 처리: 저신뢰/실패 시 수동 입력 fallback. 한도 초과여도 업로드는 항상 가능 — 차단은 AI 파싱뿐.
  • 모델 선택: 가격 차이는 무의미(장당 <1¢) — 실제 영수증 10~15장으로 품질 비교 후 결정. 모델명은 config 값.
🔒 프라이버시 — 영수증 = 개인정보 취급
왜 위험한가 고지 의무
영수증엔 이름, 카드번호 뒷자리, 멤버십 번호, 배달 주소, 약국이면 의료 정보까지 담길 수 있다. 그리고 이미지는 제3자(LLM API)로 전송된다 — 명시적 고지 대상.
첫 업로드 1회 안내 필수
"이미지는 분류를 위해 AI 서비스로 전송돼요. 민감 정보가 안 보이게 찍는 걸 권장해요."
매번 묻지 않고 1회 + 설정에서 재확인. 파싱 차감 고지와 같은 팝업으로 통합 (운영 원칙 참조).
약관 · 개인정보처리방침 동의 공개 전 필수
온보딩 가입 버튼 하단 동의 한 줄. 방침엔 수집 항목 · 제3자 전송 · 보관 기간(비회원 즉시 삭제) · 삭제 방법 포함.
일반 공개·유료화 전 방침 문구는 전문가/템플릿 검토 필수 — CCPA 및 App Store·Google Play 심사 요건.
설계로 방어 문서보다 강력
파싱 프롬프트가 품목/가격/상호/날짜만 추출 — 이름·카드번호·멤버십 번호는 추출 금지 명시. DB에 PII가 애초에 안 들어온다.
LLM은 학습 미사용 API 티어 사용. private bucket + presigned URL, 비회원 이미지 즉시 삭제는 기결정.
계정 삭제 = 데이터 전체 삭제 설정 화면 필수
방침에 쓴 약속을 지키는 실제 버튼. 이미지 포함 hard delete (운영 원칙의 삭제 2층 규칙).

운영 · 시스템 · 보안 원칙

데이터 수명 & 파싱 상태
파싱 상태 머신 quota 차감 = draft 진입 시
pending→ draft · 차감→ parsed · 저장됨 / failed · 무차감
차감 기준은 "유저가 파싱의 가치를 받았는가". 결과가 나오면 차감, 시스템이 실패하면 무차감.
저장 시 차감은 기각 — 결과만 읽고 저장 없이 이탈하는 우회를 허용하기 때문. 저장 안 된 이미지(draft·failed)는 7일 보존 후 자동 삭제: draft의 7일은 유저가 이어받을 시간("저장 안 한 영수증" 배너), failed의 7일은 실패 원인을 들여다볼 디버깅 창.
실패 로그 메타데이터 영구
failed의 이미지는 7일 후 삭제하되, 메타데이터(에러 유형·품목 수·이미지 크기·모델명)는 영구 보관 — 개인정보 없이 실패 패턴 분석.
7일 창에서 발견한 실패 유형은 재현 테스트 케이스로 승격(팀 자체 영수증·익명화 샘플). 대규모 실패 이미지 수집이 필요해지면 그때 용도 명시 옵트인으로 — 기본 보관은 하지 않음.
차감 고지
첫 파싱 때 프라이버시 안내와 통합해 1회만 팝업. 이후엔 실행 버튼이 말한다 — "파싱하기 · 9장 남음".
삭제 2층 규칙
개별 삭제는 soft delete, 계정 삭제는 hard delete.
soft = deleted_at 컬럼. quota가 유지되어 "지우고 재파싱" 무한 리필을 차단. hard = 이미지 포함 완전 파기 — 프라이버시 섹션의 약속 이행.
비용 방어 & 관측
일일 LLM 지출 상한 1주차 필수
하루 지출이 상한(예: $5)에 닿으면 체험 파싱 자동 중단 + 이메일 알림. 모든 방어가 뚫려도 최대 손해가 캡.
구현은 일일 카운터 + if문 수준. 어뷰징 방어의 핵심 원칙 = "완벽 차단"이 아니라 "뚫려도 손해 유한".
IP rate limit 1주차 필수
비인증 파싱은 IP당 시간 3회 · 일 5회. 가입 엔드포인트도 IP 제한.
FastAPI slowapi로 API rate limit 적용. OTP는 Supabase/Auth provider 측 제한과 앱 레벨 cooldown을 함께 사용. 보이지 않는 봇 체크와 이미지 사전 검증은 실제 어뷰징이 관측되면 추가. SMS 인증은 기각.
모니터링 3종 1주차 필수 전부 무료
UptimeRobot이 5분마다 /health 확인 → 다운 시 이메일 · Sentry가 부분 장애 감지 · 지출 캡 발동 알림.
/health는 단순 200이 아니라 DB에 SELECT 1을 던져 성공 시에만 200 — 서버 생존과 DB 연결을 한 번에 감지.
보안 체크리스트
Supabase RLS 전체 활성화 1주차 필수
모든 테이블에 RLS + 기본 정책 전부 거부.
anon key는 공개 키라, RLS 없이는 누구든 FastAPI를 우회해 Supabase REST로 테이블을 직접 읽는다 — 이 스택 특유의 뒷문. FastAPI는 service role 키라 영향 없음.
ledger 멤버십 검사 1주차 필수
모든 엔드포인트가 공용 의존성 하나를 통과: 토큰의 유저 → 해당 ledger 멤버인지 확인 → 아니면 404.
URL의 ledger_id만 바꿔 남의 데이터를 읽는 IDOR가 이 유형 앱의 취약점 1위. UUID 사용으로 추측도 차단.
업로드 파일 재인코딩 파싱 구현 시
magic bytes 검증 + 크기 상한 + 서버 재인코딩 한 파이프라인.
재인코딩 하나로 세 가지 해결: 악성 페이로드 무력화 + 리사이즈로 LLM 원가 절감 + EXIF 제거. EXIF의 GPS 좌표를 안 지우면 영수증 이미지가 곧 위치 이력이 된다.
프롬프트 인젝션 현 설계로 커버
영수증에 인쇄된 악성 지시문 대비 — structured output 강제 + 파싱 결과는 항상 데이터로 취급 + 확인 화면의 사람 검토.
Phase 3 챗봇의 tool calling 원칙 "LLM은 정의된 함수만 선택"이 같은 방어의 연장.
상시 스위치 상시
CORS는 프론트 도메인만 · presigned URL은 수 분 만료 + 발급 시 멤버십 검사 · 로그와 Sentry에 PII scrub · Dependabot 활성화 · JWT는 서명+만료+audience 검증.
스키마 마이그레이션
마이그레이션 = 코드
모든 스키마 변경은 Alembic revision 파일로 — PR 리뷰 필수, 최종 승인은 리드. 팀원 동기화는 alembic upgrade head 한 줄.
프로덕션 실행 전 Supabase 스냅샷. Postgres DDL은 트랜잭션이라 all-or-nothing — 반쯤 실패한 상태가 없다.

이번 카드값이 얼마 나올지,
마감일 전에 알 수 있게.

신용카드의 statement closing date 기준으로 지출 사이클을 추적하고, 영수증 사진을 AI로 파싱해 품목별로 자동 기록하는 iOS·Android 모바일 앱. 아래 데모를 직접 눌러보면서 읽어보세요.

앱 이름은 다다리를 후보로 사용 중입니다. 공식 영문 표기와 최종 로고는 TBD이며, 이 문서의 기존 자산은 그대로 유지합니다.

플랫폼 Flutter · iOS + Android 스택 Flutter · FastAPI · Supabase 통화 USD

배경 & 시장 조사

기존 가계부 앱의 한계

  • 집계 기준의 한계: 시중 가계부는 예외 없이 달력 월 기준으로 집계하지만, 카드 사용자의 실제 관심사인 "이번 카드값"은 statement closing date 기준으로 확정됨 (예: closing 21일 → 실제 청구 단위는 전월 22일~당월 21일). 이 불일치로 사용자는 도구를 쓰면서도 가장 중요한 질문에 수동 계산으로 답해야 함.
  • 입력 방식의 한계: 거래 단위 기록만 지원해 품목 데이터를 남기려면 메모란 수동 타이핑 — 현실적으로 "장보기 $52"로 뭉뚱그려지고 분석 정밀도는 상점 단위에서 멈춤.
  • 이 두 한계가 각각 핵심 기능(closing date 사이클 / 영수증 AI 파싱)으로 이어짐. 개발자 본인이 실사용 중 확인한 문제로, 첫 사용자로서 검증 루프 최단.

  • 수요 신호: 커뮤니티에서 카드별 billing cycle 탭을 나눈 직접 제작한 엑셀이 공유됨 — 제품 공백의 전형적 신호. "카드들 사이클이 제각각이라 월말 숫자가 머릿속과 안 맞는" statement-cycle confusion이 명명된 문제로 존재.
  • 포지셔닝: 홍보 리드는 파싱이 아니라 사이클 — "카드값이 얼마 나올지 마감 전에 아는 앱". 파싱은 "입력이 편한 이유"로 뒤에.
  • 경쟁 앱 리뷰에서 배운 설계 요구사항: 할인/음수 라인 처리 실패 → 합계 불일치 불만 (음수 품목 금액 허용, 할인/쿠폰 유형은 구분하지 않고 total 비교는 유지) · 축약 표기("WHL MLK 2%") 그대로 저장되는 불만 (품목명 정규화 명시) · 공격적 페이월 반감 (본 제품은 넉넉한 무료 티어 + 수동 입력 상시 가능) · 데이터 판매 불신 (프라이버시 정책이 셀링 포인트) · 상위 앱도 실측 92~94% (확인 화면 = 필수 안전망).
  • 리스크: 공백의 이유가 "아무도 안 해서"인지 "수요가 작아서"인지 미검증 — 학기 프로젝트 + 캠퍼스 소프트런칭 규모가 검증에 적합.

제품 개요

타겟 — 신용카드를 주로 쓰면서 "이번 카드값이 얼마나 나올지"를 실시간으로 알고 싶은 사람. 본인 + 미국 거주 초기 테스터가 첫 사용자.

핵심 차별점

  • 카드별 closing date 기준 사이클 측정 — 기존 앱은 대부분 매월 1일 고정. 결제금액이 확정되는 날 기준으로 "예상 카드값"을 마감 전에 보여준다.
  • 신용카드 vs 현금성 지출(debit·cash·Zelle) 구분 — 결제수단별 색상이 앱 전체를 관통하는 색 언어.
  • 영수증 업로드 → AI 파싱 → 품목별 자동 카테고리 분류.
  • Post-MVP 공유 가계부 — 커플/룸메이트용 + 가상 모임통장 (기록·잔액 추적만, 돈 보관은 안 함).

플랫폼 전략 확정

  • Flutter 단일 코드베이스로 iOS·Android 동시 지원.
  • 카메라 촬영·갤러리 선택·딥링크 등 모바일 네이티브 기능을 직접 활용.
  • 초기 MVP는 웹 없이 모바일 앱에 집중하고, TestFlight·Google Play 테스트 트랙을 거쳐 스토어 출시.

범위 & 과금 구조

  • 결제수단 등록: 신용카드(closing date 지정) / 현금성 — 카드별 색상 지정
  • 지출 수동 입력: 결제 1건에 상점·결제수단·날짜·메모와 카테고리별 품목 여러 개 저장 (백엔드 API 구현, Flutter 연동 필요)
  • 카드별 사이클 뷰: 누적액 · D-day · 진행률
  • 통합 대시보드: 30일 지출, 카드 vs 현금, 카테고리 분포, 일별 바 차트
  • 운영팀이 정한 카테고리 13개(Refund 포함)를 조회·선택 (사용자 추가·수정·삭제 없음)
  • 영수증 업로드 → Vision LLM 파싱 → 품목/가격/카테고리 JSON
  • 확인 화면: 품목별 수정 후 일괄 저장 + total 검증 배지
  • 개인화: 수정 내역을 merchant+품목 규칙으로 축적
  • 무료 파싱 카운팅 (유료화 시 그대로 재사용)
  • Pro 유료 플랜 — App Store / Google Play 인앱 구독, 회원만 결제 (구매 귀속·복구·환불) 수치·결제 레이어 미확정
  • 파싱 크레딧 팩(+20장 등) — "50장 소진 유저 비율" 확인 후
  • 공유 가계부 (커플/룸메이트용 + 가상 모임통장) + 정산 뷰 — 홈에 ledger switcher 추가. API는 처음부터 /ledgers/{id}/... 경로로 설계 (MVP 코딩 시점부터). Pro 100장 상향 or "멤버 수 × 50장" 검토
  • Pro 기능 — 캘린더 연동: 카드 마감일·예상 카드값·반복 결제일을 Apple/Google 캘린더와 연동하는 기능 검토. 네이티브 푸시 알림과 역할을 구분해 필요성 검증 후 구현.
  • 환불/취소·반복 지출 · 네이티브 확장 기능(푸시 "마감 D-3", 홈 위젯, 딥링크) 검토
  • 은행 연동(Plaid 등) — 비용·심사 이슈. 카드번호를 받지 않음 = 민감정보 제로.
  • 예산 알림, 다국어. 통화는 USD 단일(currency 컬럼만 확장 대비 유지).

인증 아키텍처 결정
Email / Password + Email Verification 확정
회원은 이메일과 비밀번호를 사용하고 이메일 인증을 완료한 뒤 계정을 활성화. 비밀번호 해싱·credential·session은 Supabase Auth가 관리하며 public.users에는 비밀번호 관련 컬럼을 두지 않음.
Guest 모드 확정
Guest 데이터는 Flutter 기기 SQLite에 저장. 회원 전환 시 인증된 user_id의 서버 데이터로 마이그레이션.
User ≠ Email 확정
앱 데이터 소유자는 Supabase Auth UUID. public.users.id = auth.users.id로 연결하고 이메일을 FK로 사용하지 않음.
Social Login / Account Linking 확장 가능
Google·Apple Sign-In은 Supabase provider로 추가 가능. 서로 다른 provider 계정 자동 병합은 하지 않고 linking 기능은 별도 요구사항으로 다룸.
인증 이메일 발송 방향 확정
Production에서는 Resend 같은 Transactional Email Provider를 Supabase custom SMTP에 연결. 인증 메일 요청에 rate limit과 resend cooldown 적용.
초기 표시 이름 UI 방향 · 생성 규칙 TBD
가입 시 랜덤 이름을 제안하고 수정·건너뛰기를 허용. GET /users/me와 PATCH /users/me는 프로필 조회·이름 수정을 지원하며 생성 규칙과 Flutter UI 연결은 TBD.
Supabase 의존성 경계
Database 확정
Supabase Managed PostgreSQL을 사용하지만 앱 데이터는 Flutter → FastAPI → Service → Repository → SQLAlchemy → PostgreSQL 경로로만 접근.
Auth 확정
Flutter는 Supabase Auth SDK로 로그인하고 JWT를 FastAPI에 전달. FastAPI 공통 Auth dependency에서 검증.
App Profile 확정
auth.users는 credential/identity를 관리하고 public.users는 nickname·plan 등 앱 전용 프로필을 관리. 동일 UUID로 1:1 연결.
Storage 임시 사용 여부 TBD
임시 이미지 저장이 필요하면 FastAPI의 Storage 경계에 격리. 영수증 원본은 영구 보관하지 않으며 삭제 시점은 구현 전 확정.
Gemini 확정
Gemini SDK·API key·timeout·retry는 공통 integration에서 관리. Prompt·category logic·total validation은 Receipt Service가 관리.
시스템 아키텍처 결정
데이터 단일 경로 확정
읽기·쓰기 모두 FastAPI 경유. Flutter 앱이 Supabase와 직접 통신하는 건 Auth뿐.
로직(사이클·quota·멤버십)은 FastAPI에 모으고, RLS는 우회 접근을 막는 추가 방어 계층으로 유지.
이미지 업로드는 서버 경유 확정
Flutter → FastAPI → 검증·재인코딩·EXIF 제거·리사이즈 → Gemini. 임시 Storage가 필요한지는 TBD.
presigned 직접 업로드는 검역 우회 경로라 기각.
파싱은 "확장 가능한 동기" 확정
MVP는 동기(타임아웃 30초, FastAPI async라 LLM 대기가 서버를 막지 않음). API 계약만 비동기 호환 — POST /receipts → {receipt_id, status}, GET 폴링 지원.
큐 도입 시 프론트 무수정, 백엔드는 인라인 호출→큐 등록만 교체. 오늘 비용 ~0으로 문만 내고 큐는 짓지 않음. 연결 끊김은 상태 머신(draft 서버 보존)이 방어.
임시 이미지 정리 미확정
원본은 영구 보관하지 않음. 임시 저장이 필요하다면 성공·실패·중단 시 삭제 시점과 정리 방식을 먼저 확정.
기존 7일 이미지 보관 및 정기 cleanup 가정은 원본 비보관 결정에 맞춰 재검토.

데이터 모델

지출 결제는 ledger에, 내 지갑의 결제수단은 user에 귀속된다. 카테고리는 전체 공통 목록이며 각 일반 품목이 이를 참조한다. 로그인 credential은 Supabase Auth가 별도로 관리한다. public.users.id = auth.users.id로 연결한다. 금액은 cents 정수로 저장·전송하고 Flutter 화면에서는 USD로 포맷한다(예: 1099 → $10.99, -1000 → -$10.00).

사용자 bootstrap 시 기본 Cash 결제수단을 한 번 생성한다. Cash는 현금 결제만 뜻하고, 은행 이체로 지출할 때는 별도의 cash-like 결제수단을 지갑에 등록한다. 계좌 사이의 단순 이체는 지출 거래가 아니다.

현행 구현과 확정 목표를 구분한다. SQLAlchemy/Alembic에는 income_sources·income_records를 포함한 모델과 결제 헤더 transactions 1건 + 필수 품목 transaction_items 1건 이상 구조가 있다. 수동 결제 생성·기간 조회·품목 추가·수정·제거·거래 soft delete API가 작성됐다. total_cents·Refund 카테고리·활성 거래 부분 인덱스 migration은 DB에 적용됐다; 인증 의존성을 대체한 실제 DB API 검증에서 생성·조회·수정·삭제가 통과했고 임시 데이터는 롤백했다. 품목 수량은 저장하지 않고 한 줄의 전체 금액을 amount_cents에 저장한다. 영수증 파싱 생성은 미구현이고, 관리자 복구·30일 경과 정리는 내부 코드만 있어 운영 연결 전이다. receipts·categorization_rules·transactions.receipt_id는 Phase 2 계획이며, categories는 공통 목록이다.

수입은 실제 기록과 예정 규칙의 생성·조회·수정, 입금 확정, 두 종류의 soft delete와 확정 Undo API가 있다. 삭제 시각과 원래 예정일을 추가한 migration까지 DB에 적용됐고 확인된 head는 c2b9befbaace이다. HTTP 경로는 임시 SQLite에서, Service·Repository의 예정 생성·확정·Undo·삭제·관리자 복구 흐름은 임시 프로필·가계부를 이용해 실제 PostgreSQL에서 확인했다. 외부 트랜잭션을 롤백한 후 관련 테이블이 0건임을 확인했다. 실제 JWT를 이용한 수입 API 검증은 아직 하지 않았다. 30일 이내 관리자 복구 함수와 만료 정리 명령을 작성하고 FK 제약을 켠 임시 DB에서 기록 보존을 확인했다. 배포 스케줄러·관리자 운영 절차·달력 통합 표시·알림 실행은 후속 작업이다.

예: Target에서 Apples(Food)·Dish soap(Living)·T-shirt(Fashion)을 한 번에 결제하면 transactions 1행과 transaction_items 3행이 생긴다. Tax/Tip은 결제 헤더에 따로 기록하고 total_cents는 품목 금액 합계와 Tax/Tip으로 계산해 저장한다. 품목 amount_cents는 수량을 별도로 저장하지 않는 한 줄의 전체 금액이며 0·음수도 허용한다. Refund 카테고리 품목은 입력 부호와 무관하게 음수로 저장하고, 품목을 수정·제거하면 총액도 다시 계산한다. 음수 품목을 할인/쿠폰 유형으로 따로 분류하지 않는다.

구현 범위: 거래 0건 DB에 결제·품목·최종 총액·Refund 카테고리 migration을 적용했다. 수동 생성·기간 조회·품목 ID 유지 및 추가·제거·거래 soft delete API를 실제 DB에 연결해 검증했고 임시 데이터는 롤백했다. 거래 검증은 인증 의존성을 대체했고, 별도의 읽기 전용 검증에서 실제 Supabase 토큰의 카테고리 조회 200과 토큰 없음·변조 토큰 401을 확인했다. 이전 스키마에 거래가 있는 DB에는 별도 품목 백필이 필요하다. 영수증 파싱 생성, 사이클·대시보드 집계 전환, 운영 스케줄러는 후속 작업이다. item_ids 배열은 두지 않는다.

설계 원칙

  • 사이클은 저장하지 않는다 확정 — closing_day 하나로 조회 시점에 계산(Demo A = 이 명세). 마감일 변경 시 과거 재계산 불필요. UI 용어는 "결제일"이 아닌 "명세서 마감일".
  • 지출과 수입을 분리 — transactions는 지출과 Refund 품목을 저장한다. 일회성·반복 예정 수입은 income_sources, 실제 입금과 Cashback은 income_records에 저장한다. 예정 없이 입력한 일회성 실제 수입은 source 없이 생성한다.
  • Receipt는 파싱 기록 (계획) — 원본 이미지는 영구 보관하지 않는다. 스캔 결제는 파싱 기록을 선택적으로 참조하고 품목은 transaction_items에 저장한다. 영수증-결제 제약 및 임시 이미지 참조 방식은 Phase 2에서 설계한다.
  • 인증 정보는 Auth에 격리 — 비밀번호·identity·session은 Supabase Auth가 관리하고 public.users에는 앱 프로필만 저장.
  • 카운터 컬럼을 두지 않는다 — 파싱 사용량은 receipts COUNT, 카드 수는 payment_method COUNT로 파생. 카운터는 동기화 버그의 원천. 게이팅 수치는 미확정
💰 Income 규칙
Paycheck · Cashback · Other 세 유형을 사용한다. 실제 입금을 바로 기록할 수도 있고, income_sources에 일회성·반복 예정 수입을 먼저 저장할 수도 있다. Paycheck의 반복은 격주·월간이며 Cashback·Other 예정 수입은 일회성이다. 예정일만으로 실제 입금을 자동 생성하지 않고 사용자의 확정으로 income_records를 만든다. Other는 금액·날짜·메모만 받는다.
Paycheck의 next_expected_date는 반복 계산 기준일로 유지한다. 표시용 adjusted_expected_date는 Bankday의 미국 Federal Reserve 은행 달력(us-fed)에서 주말·휴일을 직전 영업일로 조정한다. 연도별 휴일 목록은 공유 테이블 bank_calendar_years(year PK, holidays JSON, fetched_at)에 저장하고 당해·미래 연도는 마지막 갱신 후 30일이 지나면 다음 조회 때 갱신한다. Bankday 실패 시 저장된 목록을 사용하며 저장된 목록도 없으면 조정일은 null이다. Cashback·Other는 기준일을 그대로 표시한다.
실제 수입 수정은 해당 기록의 금액·입금일·메모와 유형별 입력값만 바꾼다. 활성 예정 수입 수정은 앞으로 적용할 예상 금액·예정일·반복 주기를 바꾸며 과거 확정 기록은 유지한다. 예정일이나 주기를 바꿀 때만 반복 기준일을 새로 잡는다.
일반 DELETE는 실제 기록 또는 활성 예정 항목의 deleted_at을 기록해 조회에서 숨긴다. 실제 기록만 삭제하면 예정 상태는 바뀌지 않고, 예정을 삭제해도 과거 실제 기록은 남는다. 확정 직후 Undo는 별도 POST /income-records/{record_id}/undo-confirmation으로 실제 기록을 숨기고 원래 예정일을 다시 연다. 다음 회차가 이미 진행됐거나 예정 규칙이 바뀌었다면 거부한다. 관리자 내부 함수는 30일 이내 삭제 수입을 복구하되 열린 회차·재확정 회차의 중복 기록 복구를 막는다. 정리 명령은 만료 기록과 규칙을 순서대로 영구 삭제하고 남은 기록의 규칙 FK를 해제한다. 배포 스케줄러와 관리자 운영 절차는 미연결이다.
Cashback은 금액·Applied to(등록 결제수단)·날짜·메모를 받으며 해당 결제수단이 현재 사용자 소유인지 확인한다. Refund는 Income 입력에서 제외하고 공통 지출 카테고리로 제공한다.
신용카드 Cashback은 received_at이 속한 사이클의 순 청구 예상액에서 차감한다. Refund 품목은 음수로 저장하며 거래의 transacted_at이 속한 사이클에서 지출을 차감한다. 원래 구매 거래는 수정하지 않는다. 과거 income_records의 Refund 행은 자동 변환하지 않는다.
알림 시간은 사용자별 설정으로 저장하지 않고 앱 정책으로 고정한다. Flutter는 Paycheck의 adjusted_expected_date가 있으면 이 날짜로 local notification을 예약하고, 값이 없으면 조정일 미확인을 표시한다. Cashback·Other는 next_expected_date를 사용한다. MVP에서는 별도 notification table을 만들지 않는다.

캘린더 거래 검색 API 작성

GET /ledgers/{ledger_id}/transactions/search는 지정한 날짜 범위에서 품목명·가게명·카테고리명의 대소문자 구분 없는 부분 일치를 찾는다. 한 품목이 여러 필드에 일치해도 한 번만 반환하며, 일치한 품목의 날짜·개수·가게 수·품목 금액 합계를 제공한다. Tax·Tip은 검색 합계에서 제외한다. 일반 캘린더는 해당 달을, 카드 화면은 사이클 기간과 선택적 payment_method_id를 전달한다. coffee가 가게명에 포함되면 그 가게의 latte 품목은 표시할 수 있으나, 두 단어를 동의어로 해석하는 의미 검색은 하지 않는다.

매번 묻지 않고 1회 + 설정에서 재확인. 파싱 차감 고지와 같은 팝업으로 통합 (운영 원칙 참조).

설계로 방어 문서보다 강력
프롬프트에는 이름·카드번호·멤버십 번호 추출 금지를 명시한다. 단, 이미지가 외부 AI에 전송되고 추출 결과·로그에 PII가 들어올 가능성은 별도 검증이 필요하다.
원본 이미지는 영구 보관하지 않는다. Gemini 등의 전송·보존·학습 정책, 임시 파일과 로그 처리, 사용자 고지는 출시 전 확인한다.
계정 삭제 = 데이터 전체 삭제 설정 화면 필수
DELETE /users/me는 개인 앱 데이터를 지우고 삭제 진행 상태를 기록한 뒤 Supabase Auth 계정을 삭제한다. Auth 실패 시 503과 진행 상태를 유지해 재시도한다. 운영자 재시도 명령은 작성했으나 자동 스케줄·모니터링은 미연결이다. 임시 이미지 삭제 및 공유 가계부의 소유권 이전·탈퇴 정책은 관련 기능 도입 전 정한다.

삭제 정책 거래 30일 soft delete
거래 전체 DELETE는 transactions.deleted_at에 UTC 시각을 기록하고 일반 조회에서 숨긴다. 30일 이내 복구 문의는 관리자 운영 절차로 처리하며 사용자용 복구 API는 없다. 기한이 지나면 품목부터, 거래를 다음에 영구 삭제한다. 품목은 Save 전 Undo만 가능하고 Save 후 제거된 품목은 영구 삭제한다. 30일 보관 데이터는 AI 학습용으로 별도 유지하지 않는다.
DELETE API·내부 복구 함수·1,000건 단위 정리 명령을 작성했다. 실제 DB에서 만료 거래·품목 삭제, 최근 삭제 거래 보존·복구를 확인한 뒤 임시 데이터를 롤백했다. 관리자 운영 경로와 매일 새벽 3시 스케줄러는 배포 환경에서 연결해야 한다. 영수증 quota와의 관계는 Phase 2에서 정한다. 계정 삭제 시 전체 데이터 삭제 방향과 원본 이미지 비보관 원칙은 유지한다.
일반 조회는 deleted_at IS NULL을 적용하고 활성 거래의 (ledger_id, transacted_at)에 PostgreSQL 부분 인덱스를 둔다. DB에서 인덱스 정의와 migration head b84e91d2c673을 확인했다.

magic bytes 검증 + 크기 상한 + 서버 재인코딩 한 파이프라인.
재인코딩 하나로 세 가지 해결: 악성 페이로드 무력화 + 리사이즈로 LLM 원가 절감 + EXIF 제거. EXIF의 GPS 좌표를 안 지우면 영수증 이미지가 곧 위치 이력이 된다.
프롬프트 인젝션 현 설계로 커버
영수증에 인쇄된 악성 지시문 대비 — structured output 강제 + 파싱 결과는 항상 데이터로 취급 + 확인 화면의 사람 검토.
Phase 3 챗봇의 tool calling 원칙 "LLM은 정의된 함수만 선택"이 같은 방어의 연장.
